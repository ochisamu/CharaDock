# Conversation memory and response latency

## Scope

Chat and Work keep their existing routing and permission boundaries. This change adds recent personal topics, memory-backed startup speech, optional decision-assisted fillers, and per-turn reasoning overrides for standalone greetings. It does not automatically promote Chat to Work.

## Memory and startup speech

The existing memory tools accept `recent` alongside durable categories. Durable memories retain their 24-entry capacity; recent topics have an independent eight-entry capacity and are eligible for retrieval for 14 days after their last update. They remain visible and forgettable through the existing memory controls while active. User statements are the source; quoted material, assistant inventions, project state and sensitive information are excluded by the tool instructions and existing storage guard.

Startup selection prefers an eligible recent personal topic, then the current scoped continuation, then a durable preference or goal. The same topic has a seven-day cooldown and all startup greetings for the character share a six-hour cooldown across launches. Selection is character-scoped; project continuation remains scoped to the active project. Generated wording is validated against a recorded evidence key. Personal topics never use the task-resumption fallback. A missing valid topic or failed memory greeting yields silence.

Before display, the runtime checks current character, scope, history, active interaction and whether the selected memory still exists unchanged. The startup speech toggle controls speech only, not storage. Desktop and Link reuse the generated greeting. Deleting a memory also prevents its cached greeting from being offered to Link.

## Waiting utterances

Decision assist and its “Brief waiting replies” setting must both be enabled. A background Codex generation prepares 14–21 short phrases (two or three each for acknowledgement, interest, empathy, shared joy, reflection, considering options and neutral waiting) from the full effective character persona. These are conversational functions, not a list of accents or personality types. Dialect, register, pronouns and form of address come from the character settings. The current configured Chat generation model and authentication are reused in a separate read-only client, with no conversation-history or speech output.

`character-filler-library.cjs` stores the vocabulary in the profile's `character-filler-candidates.json`, keyed by character and language with a versioned hash of the name, personality, complete persona and authored examples. Selection/addition and saved identity changes warm the cache in the background; existing characters are prepared when used. Unchanged profiles reuse persisted candidates across restarts. Changes invalidate eligibility immediately, and obsolete or deleted-character jobs cannot publish. Jobs deduplicate and run serially, have a 45-second deadline and back off for five minutes after failure. Complete structured output, diversity across all seven functions and mechanical text limits are validated before atomic persistence. The cache is bounded to 200 character/language entries and is optional: missing/corrupt/unwritable data never blocks Chat.

On a cache hit, the decision model receives only the generated vocabulary. During first preparation or failure, character-authored phrases and a small shared vocabulary remain a fallback; the model may decline unsuitable wording. Conversation never waits for vocabulary generation. It does not generate a new phrase on every turn.

Each decision request judges need and chooses the exact wording, including an explicit `none` option. It receives the current utterance, previous reply, effective personality, speech style, relationship, language and the last three spoken fillers for that character. Character-authored examples are style evidence, not evidence of actual progress. Explicit speech register and language constrain selection. The last three phrases are excluded after whitespace/punctuation normalization; the model also avoids close paraphrases where possible. If no suitable fresh wording remains, it stays silent. There is no keyword-based semantic filter or greeting gate in filler selection; greetings and ordinary thanks normally receive silence from the model. Mechanical checks only bound length/count and reject malformed text, links and markup. The model rejects unobserved action/completion claims, unsuitable tone and candidate instructions.

Speech requires at least 0.7 in the model's need score and a valid non-`none` choice. The answer starts independently. While no visible answer has started, the runtime judges at two, five and nine seconds (at most three attempts, each bounded to 900 ms). Each request carries actual elapsed wait and observed search-start/completion events; no search is invented from the wording of the request. Fresh-information/news requests are distinguished from instantly answerable facts. An earlier silent or failed decision can be reconsidered, but at most one filler is emitted per turn. First visible answer text, completion or cancellation closes it; empty/hidden deltas do not. Spoken fillers retain a 30-second cooldown. Diagnostics record scores, elapsed time and decision/skip reasons without user or candidate text. The selected wording is never randomly replaced. A changed turn, character or language also cancels delivery.

The existing shared announcement/speech queue delivers the phrase to desktop and Link; it is never saved as a conversation turn. Work keeps its existing grounded progress commentary. Live retains its own speech ownership and receives no extra filler. Conversation-time selection remains bounded to prepared candidates; arbitrary voice styles are handled during background generation instead of being enumerated by the application.

## Greeting effort

Standalone greetings and thanks without attachments, explicit tool selection or a pending question may use `none` (when supported) or `low`. Context-dependent confirmations retain their configured effort. Model catalog capabilities take precedence; known model fallbacks are conservative and unknown models keep their setting. The override is passed to `turn/start` without calling `setReasoningEffort`, so it does not invalidate the thread or affect the next turn. Typed Live requests that go through Codex also use this mechanism. Native Realtime voice generation does not expose this per-turn Codex effort control.
